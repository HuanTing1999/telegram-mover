# 技术说明与配置参考

Python 3.11+、Telethon 1.45.0、MTProto 用户账号。手机号＋验证码交互登录；账号启用两步验证时，在验证码通过后按需输入该账号的两步验证密码。只持久化授权 session，不保存验证码或两步验证密码；不使用 Bot API、Bot Token、二维码或第三方登录。

Windows 直接双击根目录的 `TelegramMover.exe`打开图形窗口，无需另装 Python 或使用终端。可在窗口里填写应用凭证、使用手机号和验证码登录并按需完成两步验证、配置任务、预览广告、开始/安全停止及查看日志。设置默认保存在 EXE 旁的 `config.toml`，已有文件不会自动覆盖。详细窗口操作见 [软件说明书](USER_GUIDE.md)。

同一软件共用一套应用凭证；**添加或切换其他账号不需要重新申请或填写 API**。账号列表保存各账号独立的本地会话，日常通过“添加账号 / 切换账号”操作。应用设置完成后自动折叠并读取，也支持分发者显式提供软件预置凭证。详见 [多账号与应用设置](../ACCOUNTS.md)。

登录成功后，手机号、验证码与密码区域自动收起，日常只显示紧凑的账号栏；需要换号或重新登录时再展开。源和目标输入框旁提供“选择”，从当前账号可见的频道、群组（含归档）中搜索选取，不必手动查 ID。选择列表是只读操作，不自动入群、不发送内容。数字、时间和下拉设置不再通过鼠标滚轮改变，滚轮只用于滚动页面。

图形界面提供“搬运任务 / 广告过滤 / 发送限速 / 运行记录”四页；广告规则针对已确认的文字、链接和推广按钮场景，详见 **[广告过滤说明](../AD_FILTERS.md)**。默认启用高置信关键词，支持正则、隐藏链接、按钮和域名规则、白名单，以及预览后手动屏蔽整条消息/相册。命中后先记录 `filtered_ad` 再推进增量游标，不下载、不发送、不占发送次数；纯下载备份默认仍保留完整内容。

## 群组里的话题与下载速度

“群组里的多个小群”是 Telegram 话题。点击源或目标旁的“选择”，先选择话题群，再在第二层选择具体话题；也可以选“整个群 / 所有话题”（源）或默认位置（目标）。确认第二层后才写入选择，取消不会改变原配置。主界面显示所选话题范围，鼠标停留可查看完整名称。

源选择整个群时，所有话题的消息按消息顺序合并读取，并发送到所选目标位置；软件不会自动创建或复制一整套话题结构。要对应搬运，请分别选择源话题和目标话题运行，各范围有独立增量进度。同群搬运只允许两个不重叠的明确话题，禁止从整个群搬回该群，以免循环复制。

`sync.source_topic_id` 与 `sync.target_topic_id` 默认均为 `0`，兼容旧配置；源 `0` 表示整个群，话题 `1` 为综合话题，目标 `0`/`1` 都发送到综合默认位置。话题列表直接从 Telegram 读取，不能把频道的 linked discussion 评论根当成话题 ID。粘贴帖子链接仍只识别父聊天，需要限定话题时请通过选择器指定。

新版 EXE 已包含 cryptg 原生媒体加解密加速，不需要用户另装组件；源码环境通过 requirements 安装。下载进度同时显示已完成大小和实际 MB/s，完成的本地备份可复用。加速改善本机处理瓶颈，实际传输速度还受网络和 Telegram 服务端影响；不会通过取消发送限速或增加大量并行请求提速。当前未使用真实账号进行端到端下载或发帖验收。

大文件下载现使用受限的分块请求流水线，默认最多 4 个请求同时读取；在主页面“高级设置”的“下载并行数”中可设为 1–8，对应 `[storage] download_connections = 4`。1 表示普通单路。已知大小且至少 2 MiB 的普通 document 媒体使用并行；小文件、照片、未知大小或需要 CDN 的媒体使用 Telethon 原下载流程。接收进度按实际下载字节汇总，文件按顺序写入并检查最终长度，完整落盘后才转发。并行数不改变历史任务或发送限速，也不保证绕过网络或服务端速度限制。

直接转发不会下载文件。出现 `ChatForwardsRestrictedError` 表示源聊天启用了保护内容，Telegram 明确拒绝转发，与下载速度和发送间隔无关；软件显示中文原因，已知保护状态时在下载前停止，不会自动改用重传。请改用允许转发的源，或由源管理员调整设置。依据：[Telegram 转发错误说明](https://core.telegram.org/method/messages.forwardMessages)。

## 下载文件夹与已转发文件清理

默认媒体保存在 EXE 旁的 `downloads`。在“搬运任务”页的“下载文件夹”中点击“选择文件夹”，可改到其他硬盘；“打开”会打开当前实际目录。相对路径以**当前配置文件所在目录**为准，不随启动位置变化。点击“保存配置”或开始任务后，所选目录会持久保存到 `storage.download_dir`。起始消息 ID 和循环间隔在“高级设置：起点、循环与会话”中。

选择“下载留档后转发”（`download_then_forward`）时，先将本条消息或整个相册的媒体下载到所选目录，下载完成后才转发原消息。更换目录用于新消息及未完成的下载，不会自动搬动旧文件，也不会重跑已完成消息；需要清理旧目录时，请先选回对应目录。

“一键清理已转发文件”只清理当前目录中、本工具登记且已确认完成 `download_then_forward` 转发的媒体。“转发成功后自动清理本次下载文件”默认关闭，仅在该模式生效；对应 `[storage] auto_cleanup_forwarded = false`。自动清理限于本次成功转发的下载，手动清理可处理当前目录的历史已转发文件。

未发送、转发失败、发送结果待确认（pending）、已被修改或未登记的文件会保留；重传和纯下载备份文件也保留。旧版记录若缺少文件身份校验信息，会保留并提示人工核对。清理只处理符合条件的本地媒体，不清除消息映射、同步进度或待确认记录；清理结果、时间和错误留在数据库供核对。

以下终端命令适用于源码开发与维护；日常使用图形界面即可。预览只读，不要求填写目标，不发送媒体或推进搬运进度。软件没有 OCR，不声称能可靠识别纯图片/视频广告。

新版已加入统一限速与账号停止保护，详见 **[发送限制与恢复说明](../LIMITS.md)**。默认两次发送操作至少间隔 15 秒，滚动 60 秒 / 1 小时 / 24 小时分别最多尝试 20 / 200 / 1,000 条，单次进程最多 200 条、60 分钟。正文、评论与相册成员按同一账号一起计数，纯下载不占发送条数。次数和服务器要求的冷却保存到 SQLite，重启不清空。上述数值是本工具的策略，不是 Telegram 的官方安全阈值。

遇到明确 `FLOOD_WAIT` / `SLOWMODE_WAIT` 时先保存等待期限，再在允许范围内恢复；账号反垃圾限制或冻结会持久停止，等待人工检查。未确认发送的 pending 保护继续有效。

## 先说明两个接口边界

1. **频道/群组正文完整支持四种模式；普通频道评论区支持重传和纯下载。原生“直接转发到某条评论线程”不受当前 API 支持。** Telethon 的 `forward_messages()` 没有 `reply_to` 参数。底层 `messages.forwardMessages.top_msg_id` 是论坛话题参数；其 `reply_to` 只支持 monoforum，不适用于普通频道的 linked discussion。把这些参数当作评论根使用会报错或发到群主聊天。本工具会在发送任何正文之前拒绝这种评论配置，不静默改模式。可用 `mode="forward"` 搭配 `comment_mode="reupload"`，或关闭评论同步。
2. **重传保证下载文件后上传本地字节、生成目标消息且无转发头，不承诺独一的新文件 ID 或搜索排名/归属。** MTProto 使用 document/photo ID 等媒体引用，不能套用 Bot API 的 `file_id` 概念。Telethon 的 `allow_cache=False` 当前只是兼容参数，真正强制上传的是传本地文件路径；本程序两者都使用。Telegram 服务器的去重、频道可见性和搜索索引由服务端决定。

依据：[Telethon 客户端接口](https://docs.telethon.dev/en/stable/modules/client.html)、[Telegram forwardMessages 参数](https://core.telegram.org/method/messages.forwardMessages)、[Telegram 文件上传](https://core.telegram.org/api/files)。

## 安装与配置

在本目录执行（Windows PowerShell）：

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item config.example.toml config.toml
```

到 [my.telegram.org/apps](https://my.telegram.org/apps) 自行申请 API_ID、API_HASH。没有预置应用凭证。建议在当前终端设置环境变量：

```powershell
$env:API_ID = "填入你自己的应用ID"
$env:API_HASH = "填入你自己的32位API_HASH"
```

也可在 `config.toml` 的 `[telegram]` 中填 `api_id = 整数`、`api_hash = "32位字符串"`。环境变量优先。工具不接受配置中的手机号、验证码、密码或 token 字段。

修改 `config.toml` 中的 `source`、`target`。支持 `@username`、公开 `https://t.me/username`、完整公开帖子链接 `https://t.me/username/帖子ID`、私有帖子链接 `https://t.me/c/内部频道ID/帖子ID`，以及 `-100…` 聊天 ID（整数或纯数字字符串均可）。也支持公开预览与话题帖子路径；软件先提取所属聊天，再交给 Telethon 识别，不把整条帖子 URL 当作用户名。

**粘贴帖子链接只用于识别所属频道／群组，不会将该帖子自动设为搬运起点。** 起点仍由 `start_id` 和已保存的增量进度共同决定。私有频道需提前用该账号加入；邀请 URL 只检查是否已加入，不自动入群。数字 ID 可能需要从当前账号的聊天列表加载 access_hash；若仍无访问权限，会明确指出源还是目标并提示重新选择。同名聊天不会随意选取，应通过“选择”确认。链接格式依据 [Telegram 官方说明](https://core.telegram.org/api/links#message-links)。

目标频道需要该用户具备发帖权限，目标讨论组需要发送权限。源为频道且开启评论同步发送时，目标必须为已关联讨论组的频道，否则提前报错。普通群组没有独立的频道评论区，群消息直接作为正文处理。

```powershell
# 只验证配置，不连接
.\.venv\Scripts\python.exe main.py --validate-config
# 手机号＋验证码登录，按需完成两步验证，并读取检查聊天/评论区；不搬运
.\.venv\Scripts\python.exe main.py --check
# 跑一轮，忽略配置里的循环间隔
.\.venv\Scripts\python.exe main.py --once
# 按 poll_interval 循环检查（0 代表只跑一轮）
.\.venv\Scripts\python.exe main.py
```

首次登录输入带国际区号的手机号（菲律宾 `+63…`、美国 `+1…`、英国 `+44…`、香港 `+852…` 等均支持），不会自动添加国家码。号码可含空格、括号、连字符或使用 `00` 国际前缀。点击“发送验证码”后，账号区域会显示连接进度或缺少应用凭证、网络超时等错误；可在同一区域停止等待。验证码可能发到已有 Telegram 客户端，也可能通过短信，渠道由 Telegram 决定。收到后输入验证码，按回车或点击“验证并登录”；支持粘贴带空格、连字符的纯数字验证码，不会输入后自动提交。成功后保存当前账号的授权 session；添加账号时各自使用独立会话，原有会话保留原位置。下次复用有效授权，不再询问手机、验证码或两步验证密码。

**支持启用 Telegram 两步验证的账号。** 只有 Telegram 在验证码通过后返回 `SessionPasswordNeededError` 时，工具才会要求该账号的两步验证密码；未启用时不会询问。终端输入默认隐藏显示。密码按原样提交，前后空格属于密码，不能自动去除；空字符串不会发给 Telegram。终端连续 3 次输入无效或为空会停止本次登录，不重新发送验证码。密码只用于本次身份验证，不写入配置或日志，也不加入账号索引；授权后仅保存 session。忘记密码时请使用 Telegram 官方的恢复流程。

源码启动图形界面使用 `python gui_main.py`；命令行指定配置使用 `python main.py --config 配置文件路径`。命令应在仓库根目录执行。

## 验证码输错与重新获取

验证码输错后，原输入会清空，可以重新输入正确验证码；不会自动反复提交或自动发码。账号区域提供独立的“重新获取验证码”按钮：Telegram 提供下一发送渠道时，等倒计时结束后可手动申请，并使用新请求返回的验证状态登录。验证码通过且账号启用两步验证时，会突出显示独立的“第2步 · 两步验证密码”区域，并收起手机号、验证码和获取入口；直接填写你在 Telegram 设置的两步验证密码即可，不需要等待重发倒计时。

重发倒计时属于本软件当前发码请求，按服务端响应计算，不是验证码或两步验证密码的有效期，也不要求与官方客户端另一请求的倒计时一致。进入两步密码步骤后不显示重发倒计时。

发送渠道和下一渠道按 Telegram 的实际响应显示。显示“Telegram 官方客户端”时，请检查该号码已登录设备中的 Telegram 服务消息；不代表已经发送手机短信。未提供下一渠道、渠道不可用或受到发送限制时，软件会明确说明，不强制短信、不自动切换第三方登录。

也可以取消本次登录后重新申请。取消、验证码过期或连续输错结束挑战会清除旧的本地请求状态，保留原 session 和已登录账号；登录服务器要求的等待会保存在会话目录旁的 `auth_cooldowns.sqlite3`，重启仍需等到期限。该文件仅保存散列索引和等待期限，不保存手机号、验证码或验证码请求 hash。网络结果不明时停止等待并显示防重复请求提示，不盲目循环发码。

接口依据：[Telegram 授权流程](https://core.telegram.org/api/auth)、[验证码响应及下一渠道](https://core.telegram.org/constructor/auth.sentCode)、[重新发送验证码](https://core.telegram.org/method/auth.resendCode)。

## 模式

| 正文 mode | 下载本地媒体 | 目标动作 | 转发引用 |
|---|---|---|---|
| `download_only` | 是 | 不发送；文字/原始消息元数据记录进 SQLite | 无 |
| `forward` | 否 | `client.forward_messages()` | 保留 |
| `reupload` | 是 | 本地文件交给 `send_file(..., allow_cache=False)`；纯文字 `send_message()` | 无转发头 |
| `download_then_forward` | 是 | 下载后仍转发原消息 | 保留，不是重传 |

`comment_mode` 独立于 `mode`；默认 `reupload`，正文为 `download_only` 时默认也纯下载。不填写可使用默认值；示例配置中显式填了 `reupload`，因此改为纯下载时请同时修改：

```toml
[sync]
source = "@source_channel"
mode = "download_only"
sync_comments = true
comment_mode = "download_only"
poll_interval = 60
```

直接转发正文、重传评论的常用组合：

```toml
[sync]
source = "@source_channel"
target = "@target_channel"
mode = "forward"
sync_comments = true
comment_mode = "reupload"
poll_interval = 60
```

两段配置均仅是 `[sync]` 示例，仍需保留有效 API 配置或环境变量。

## 评论、相册与增量

- 先用 `GetFullChannelRequest` 得到双方 `linked_chat_id`，再用 `GetDiscussionMessageRequest` 为每条帖子解析真实讨论根。返回结果会按讨论组 peer 过滤，不能把频道帖子 ID 当作讨论组根 ID。
- 使用 `iter_messages(source_linked_chat, reply_to=source_root, min_id=线程游标, reverse=True)` 拉取新增评论。每轮检查所有已记录帖子的线程，因此旧帖新评论也会同步；需要对旧线程发增量查询，但不会全量重复下载、发送历史内容。
- 对目标讨论组根用 `reply_to=target_root` 重发文字/重传媒体。新帖子根尚未生成会短暂重试；仍不存在则停止保留正文映射，下次继续评论，不重发正文。已记录的目标根删除/不可读时停止。
- 评论统一回复目标帖子根，不复刻评论之间的多层回复树；所有重发内容由登录账号发布。评论原作者、时间、实体等保存在 SQLite 元数据中。
- `grouped_id` 相同的相邻消息按 ID 顺序作为完整媒体组提交；一次最多 10 个成员。相册标题、格式实体按成员配对保存。相册的多个帖子 ID 若共用评论根，只处理一次该线程。
- `settle_seconds`（示例 5 秒）内的新消息和尾部相册留到下一轮，降低相册尚未到齐时被处理的风险。单次执行时需稍后再运行。若 `start_id` 落在相册中间会停止，要求改到整组之前。
- 主游标和消息 ID 映射随整批结果在 SQLite 同一事务提交；失败不会越过。未完成文件使用 `.part`，下载成功后再替换最终文件；记录实际路径、大小。重传后的本地文件保留用于审计，不自动删除。
- 下载文件名保留经路径安全处理的原名并加消息 ID；相册内音视频的细节属性由 Telethon 重新识别，不能保证所有原媒体属性逐一复刻。
- 图片、普通文件、视频、音频等可下载媒体支持重传；单文件尽量保留 document 属性。相册文件类型识别由 Telethon 根据扩展名完成。重传投票、联系人、位置等非文件媒体会明确停止，不丢弃内容冒充成功；纯下载仍记录其元数据。服务消息记为 `skipped_service`。
- 只同步**新增**消息与评论，不镜像编辑、撤回、反应、浏览数或成员信息。目标消息不能保留原作者身份、原发布时间。

`start_id=0` 初次从可见历史起点处理；其它数值只处理 ID **大于**该值的正文。评论从所选正文的讨论线程开始备份。后续起点为 `max(start_id, 已保存游标)`；不要在已有任务上随意提高它，否则会主动跳过未处理内容。

任务按账号、解析后的源/目标、模式和已启用的 linked chat 隔离。**修改模式、切换评论发送/备份模式、启闭评论导致链接状态变化、切换聊天或账号会建立独立任务，可能从 start_id 重新发送**。测试不同模式宜使用不同目标和配置文件。源/目标为同一个聊天会被拒绝。

## 数据与恢复

`data/state.sqlite3` 包含：

| 表 | 记录内容 |
|---|---|
| `messages` | 源正文/评论 ID → 目标 ID、原文、完整消息元数据、grouped_id |
| `threads` | 源帖子 ID → 源根、目标帖子 ID、目标讨论根与讨论组 ID |
| `cursors` | 正文主进度及每个评论线程进度 |
| `downloads` | 每条源消息最新的下载路径、大小、目录和文件身份信息，以及清理状态 |
| `download_files` | 各目录中已登记下载文件的历史；保留清理状态、时间和错误审计，换目录不丢失旧路径记录 |
| `operations` | 正在发送或发送结果未能确认的操作 |
| `routes` | 任务签名 |
| `limit_events` / `limit_accounts` / `limit_peers` | 同账号发送尝试预算、账号/聊天冷却、账号停止原因 |

正常重跑跳过完成内容。网络可能在 Telegram 接受发送之后、返回目标 ID 之前中断，本地数据库无法与 Telegram 共同做事务。为避免盲目重传产生副本，工具先持久记录操作，再发送；网络中断、5xx、超时等结果不明时保留 pending 并停止。**不宣称网络故障下自动实现严格 exactly-once。** 明确拒绝的 4xx 不推进游标；只有可识别的等待错误会在配置范围内重试，账号限制、冻结或权限错误会停止。服务器冷却先持久化，`sync.max_flood_wait` 和 `limits.max_auto_wait` 同时约束自动等待；超过任一上限就结束，稍后重跑仍需遵守冷却。

Telegram 若对大频道视频返回 `video_processing_pending`，目标消息尚在服务端处理，本工具也会保留 pending，避免把临时排队 ID 错存为最终帖子 ID。待处理完成后按相同恢复步骤核对并清理目标，再重试；此类视频尚未实现全自动最终 ID 追踪。

遇到待确认操作：

图形界面在“运行记录 → 待核对发送”中显示当前数据库的整批源消息 ID、源/目标及话题和创建时间（UTC）。先在目标人工核对，并清理这批可能已经发送的整组内容；选中对应记录、勾选核对声明后，才能解除该批本地阻塞。解除不删除目标消息、不立即发送，不清空映射、增量进度或发送额度；下次运行才处理尚未完成的内容。列表与记录变化时需要重新刷新，部分映射不能直接解除。

普通转发和文字发送最多等待 90 秒确认，上传按实际进度计算连续 120 秒无进展才停止。安全停止会等待当前结果直到这个边界；结果无法确认时保留 pending、断开并丢弃原连接，不自动重新发送。明确权限/保护内容拒绝不归为“待核对”，也不会笼统声称已保存等待时间。丢失响应和服务器 5xx 都可能已经成功发送，不能将超时当成发送失败后直接重试；依据：[Telegram 消息响应与去重说明](https://core.telegram.org/api/updates)。

源码维护者也可使用以下本地命令：

```powershell
python main.py --show-pending
```

根据 `key`、`source_ids` 和原帖核对目标频道/讨论区，**人工删除该次已经发送的整批内容，或确认该次完全未发送**。确保目标已清理后才解除阻塞：

```powershell
python main.py --retry-pending "post:0:123,124" --route "show-pending输出的route"
python main.py --once
```

上述 ID 仅为命令示例，替换为真实输出。解除阻塞的命令本身不发送内容；下一次会重新处理。若不清理已接受但未确认的内容，人工解除后仍会产生重复。若消息映射已经成功落库而只是 pending 清理前退出，下次启动会自动清除该已完成标记。

同一 session/数据库使用进程锁，禁止多进程同时使用。备份数据时先停止程序，再复制整个 `data/` 和 `downloads/`；session 可直接授权操作账号，应与 API_HASH 一并妥善保管，勿提交版本库。

查看限速状态可用 `python main.py --limits-status`。遇到持久账号停止时，先在官方客户端核对原因，恢复后再执行 `python main.py --resume-account 账号数字ID`；该操作不连接 Telegram，也不清除计数、冷却或 pending。完整步骤见 [LIMITS.md](../LIMITS.md)。旧配置不填 `[limits]` 也会自动采用默认策略；调整限速配置不会建立新 route 或清空发送记录。

## 开始搬运后没有看到内容

先查看账号是否已登录，以及当前任务的具体步骤。连接会话、解析源和目标、检查评论区、读取新消息都发生在发送之前；界面出现“等待 1 秒：最小请求间隔”是正常读取间隔，**不代表发送成功**。长等待显示原因和剩余时间，按最多 30 秒的分段刷新；等待结束会回到原来的操作步骤。请结合“已发送消息”计数、拦截记录和目标聊天判断结果。

登录阶段的 `AUTH_RESTART` 表示授权流程需要重新开始，和搬运额度、1 秒读取间隔是独立问题。按账号区域提示完成登录或重新获取验证码，再开始任务；不要因该错误反复清空搬运数据库或申请新的应用凭证。

只读请求超时会指出正在解析、检查或读取的步骤并停止本次操作。检查网络和聊天访问权限后再运行，已保存的映射保留，未处理消息不会记为成功。发送或上传结果未确认则应先核对 pending，按照上文恢复流程处理，不能直接当作安全重试。

若流程完成但仍为零条，核对源和目标是否已填写并保存、是否使用纯下载模式、消息是否已在历史游标之前、尾部消息是否仍在 `settle_seconds` 等待期，以及内容是否被广告规则整组拦截。只读预览和“检查连接与评论区”本身都不会发送内容。限额、活动时段和服务端冷却的具体含义见 [LIMITS.md](../LIMITS.md)。

## 重新生成 Windows EXE

在 Windows 64 位 Python 环境安装 `requirements-build.txt`，运行 `build_windows.ps1 -Python 你的Python路径`。构建使用 `gui_main.py`、PySide6 6.11.2 和 PyInstaller 6.22.3 的 `--windowed` 单文件方式，默认输出到源码文件夹的上一级。旧控制台 EXE 首次会备份到 `.build/backups/`，已有配置不覆盖。脚本会临时隔离构建 PATH 并清理收集缓存，避免其他软件的同名 DLL 混入；结束后恢复 PATH。构建只内嵌无凭证模板，不打包真实配置、session、数据库、下载内容或测试数据。
